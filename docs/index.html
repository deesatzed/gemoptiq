Cortex Sentinel

Vibe coding is powerful. It can also wreck your repo fast. Cortex Sentinel watches a local coding agent, blocks obviously dangerous actions, asks you before gray-area actions, and saves a trace so you can see what happened.

What is the boundary?

This is supervision and evidence. It is not a magic sandbox or a guarantee that every unsafe side effect is impossible.

The problem it was designed to solve

Vibe coding usually starts with a vague prompt like "fix this" or "build the feature." The agent can be useful, but it may also take actions you did not mean to authorize.

01

It can touch secrets

A coding agent may inspect or modify `.env`, SSH files, tokens, or other sensitive paths while trying to debug.

02

It can run risky commands

Commands like `curl ... | sh`, network calls, deploy commands, and shell edits can create damage faster than a beginner can read them.

03

It can delete or overwrite work

Deletes and broad rewrites may be technically valid but still wrong for your assignment, project, or repo state.

04

It can leave no trail

After a long session, you may not know which action was allowed, blocked, reviewed, or rolled back.

Before and after Sentinel

The goal is not to stop you from using agents. The goal is to make agent work slower at the dangerous moments and clearer after the run.

Vibe coding without Sentinel

  • You ask for a broad fix.
  • The agent runs commands you may not fully understand.
  • Secret-like files and protected paths are just files unless you notice.
  • After the session, you reconstruct what happened from terminal scrollback.
  • If something breaks, you may not know which action caused it.

Vibe coding with Sentinel

  • You run the agent through `sentinel run`.
  • Hard policy blocks known-dangerous actions.
  • Gray-area actions wait for human approval.
  • Protected-file writes can be detected and rolled back in supported cases.
  • The trace gives you a replayable audit trail.

What happens step by step

This is the full loop in beginner language. Sentinel sits between you and the agent process.

1

You start an agent

Example: `sentinel run --config sentinel.yaml -- codex`. Sentinel launches the child process locally.

2

It watches requests

It looks for prompts, risky command text, and file effects in the workspace.

3

Policy acts first

Protected files, secrets, network effects, and deploy attempts are hard policy decisions.

4

You approve gray areas

Ambiguous or delete-like actions can pause and wait for approve, block, pause, kill, or override.

5

The trace remembers

Later, trace replay shows decisions, effects, user actions, rollback events, and digests.

What it can and cannot do

This section is here on purpose. A beginner should know the difference between supervision, audit evidence, and true containment.

Can do

Launch local agent commands, classify risky effects, block hard-policy violations, pause for human approval, record traces, and replay them later.

Can sometimes repair

For supported protected-file effects, polling enforcement can suspend the runner and roll back a created, modified, or deleted protected path.

Cannot promise

It is not a kernel sandbox, not a container, not a cloud authorization service, and not proof that every unsafe side effect is impossible.

Try the safe path first

Start with a harmless command and readiness checks before putting a real agent on a real project. Use disposable workspaces when testing real agents. 

pip install -e .
sentinel check-env
sentinel readiness --no-run
sentinel run --config sentinel.yaml -- python -c "print('ready')"
sentinel trace replay --format text .sentinel/traces/<session>.jsonl
Cortex Sentinel is a local-first safety console for coding-agent supervision. Keep secrets out of prompts and traces, and use disposable workspaces for real-agent validation.
